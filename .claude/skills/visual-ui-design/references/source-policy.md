# Source policy and precedence

Classify the decision before selecting a source.

| Tier | Source kind | May influence |
|---|---|---|
| A | Official platform/standard | Rules, constraints, native conventions |
| B | Mature production design system | Components, tokens, system rationale |
| C | Research/human factors | Evidence and tradeoffs |
| D | Product pattern database | Observed precedent and comparisons |
| E | Inspiration gallery | Visual exploration only |
| F | Implementation library | Feasible primitives after design decisions |

## Precedence

1. For platform decisions, use the platform owner first.
2. For accessibility, use W3C/WAI and official platform accessibility guidance.
3. For component/pattern decisions, use platform guidance and mature design systems.
4. For usability rationale, use research-oriented sources.
5. For precedent, use product-pattern databases.
6. For visual expression, use inspiration sources last.
7. Never let a lower-authority source override a higher-authority requirement without explicit justification.

Do not use Dribbble, Behance, Awwwards, or similar galleries as proof of usability, accessibility, component semantics, or platform compliance. Do not copy a proprietary interface; extract general patterns and verify them against requirements.

Record source name, URL, access date, claim supported, authority tier, and whether the conclusion is sourced or inferred. If a source is unavailable or behind authentication, continue with available authoritative evidence and disclose the limitation when material.
