# Artifact Modes

Choose the smallest deliverable that proves the requested visual decision.

| Request | Minimum complete deliverable |
| --- | --- |
| Direction or early alignment | Design Read, calibrated dials, selected thesis, reference reasoning, system snapshot |
| High-fidelity screen or redesign | Rendered screen(s) at representative size, key states, concise decision record, critique-and-correction evidence |
| Component family | Rendered component board with anatomy, variants, states, content stress cases, tokens, and usage rules |
| Design system | Semantic foundations, representative rendered components and states, responsive/platform rules, adoption notes |
| Visual critique | Annotated or location-specific findings, prioritized corrections, and a revised render when editing is authorized |
| Handoff | Rendered source of truth plus semantic tokens, component behavior, state matrix, responsive rules, and acceptance checks |

## Tool Routing

Use the best available surface:

- a design tool when an editable design artifact is required;
- a small HTML/CSS or framework prototype when exact layout, responsive behavior, or component states must be rendered;
- image generation for mood, art direction, imagery, or visual exploration, not as the source of truth for precise UI behavior;
- screenshots and browser inspection to critique an existing implementation;
- Markdown only when the user requested direction/specification or rendering is unavailable.

Do not turn a visual-design task into production engineering. A renderable prototype should be the smallest artifact needed to validate the design and must clearly hand off production concerns downstream.
