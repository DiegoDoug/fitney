# Evaluation Methods

Read this reference when planning or assessing heuristic reviews, usability tests, surveys, metrics, or longitudinal UX research.

## Choose the Method From the Question

| Research question | Suitable evidence |
| --- | --- |
| Can users complete the task? | Completion, errors, recovery, time, observation |
| Why do users struggle? | Moderated observation, cautious think-aloud, interview after behavior |
| How usable does the product feel? | UMUX or another validated perceived-usability instrument |
| What kind of engagement occurs? | User Engagement Scale dimensions plus product-relevant behavior |
| How does experience change over time? | Longitudinal logging, diary study, or UX Curve retrospective method |
| Which design problems are apparent before testing? | Structured heuristic evaluation tied to scenarios |
| Which concept should advance? | Comparative task evidence aligned with explicit decision criteria |

Do not choose a method simply because it is familiar or inexpensive. State what evidence would change the product decision.

## Heuristic Evaluation

Use heuristics as inspection prompts, not as proof that an interface is usable. Tie every reported violation to a user, scenario, task, and plausible consequence.

Use a consistent report structure:

- interface location and state;
- observed condition;
- applicable principle;
- affected task and user;
- expected consequence;
- severity rationale;
- proposed correction;
- verification method.

The comparison by Hvannberg, Law, and Lárusdóttir did not establish a clear effectiveness advantage for the evaluated Nielsen or Gerhardt-Powals heuristic sets or reporting media. Its stronger reusable contribution is structured comparison and problem reporting. Avoid claiming that a chosen heuristic set is universally superior.

## Usability-Test Tasks

Build task coverage from the product's important scenarios. Include:

- high-frequency tasks;
- high-consequence tasks;
- first-use or setup tasks;
- recovery from likely errors;
- tasks spanning critical roles or contexts;
- important states such as empty, interrupted, unavailable, and destructive.

Write goals without revealing the control labels or exact steps being tested. Pilot tasks before recruitment when practical.

Lindgaard and Chattratichart found task coverage correlated with problem discovery in their analysis of commercial usability teams, while participant count did not show the same relationship. Apply this as a warning against weak task selection, not as evidence that participant count never matters.

## Sample Size

Reject universal participant-count formulas. Determine the sample in relation to:

- formative versus summative purpose;
- qualitative discovery versus statistical estimation;
- number and diversity of user groups;
- task and workflow coverage;
- expected variability and problem visibility;
- safety, financial, legal, or operational consequence;
- iteration plan and stopping criteria.

Small formative rounds can be useful when repeated, but they do not establish population-level rates or compliance. Schmettow specifically challenges magic-number rules for usability problem discovery.

Any starting count must be paired with a stopping or continuation rule. Depending on the question, continue or revise the study when:

- important task or participant segments remain uncovered;
- new material problem types continue to appear;
- observed behavior varies enough that the product decision remains unstable;
- a comparison lacks the precision required for the decision;
- or a predefined risk or confidence threshold has not been met.

Use a pilot to revise tasks, measures, timing, and recruitment assumptions. Do not present a planning estimate as a research-backed universal sample size.

## Existing Product Evidence

Before finalizing priorities for an existing product, inspect available analytics, support tickets, field observations, prior studies, and failure or recovery data. These sources can refine frequency and consequence estimates but have different biases. Preserve conflicts between reported preference, observed behavior, and operational data.

If a user group or role is weakly described, create discovery questions and representative recruitment criteria for that group. Do not fill the gap with confident invented needs.

## Measures

### Behavioral

Use completion, error type, recovery, time, path deviation, assistance, abandonment, and downstream outcome when relevant. Define success and failure before observation.

### Perceived usability

UMUX is a four-item subjective scale designed to align with the ISO 9241-11 concept of usability and correlate with the System Usability Scale. It measures perceived usability; it does not replace behavioral evidence.

### Engagement

The User Engagement Scale separates perceived usability, aesthetics, focused attention, felt involvement, novelty, and endurability. Select it only when engagement is an explicit product outcome and interpret its dimensions rather than relying only on a total score.

### Long-term experience

Use UX Curve when learning, adoption, changing attractiveness, loyalty, or accumulated experience matters. It is retrospective and qualitative; memory and reconstruction can affect the account. Combine it with longitudinal behavioral evidence when consequential decisions require stronger support.

## Synthesis

Keep separate:

- observed behavior;
- participant explanation;
- questionnaire result;
- evaluator inference;
- product decision.

Look for convergence, but preserve disagreement. For example, users may rate an attractive interface highly while committing serious task errors. Report both findings and design validation to address the discrepancy.
